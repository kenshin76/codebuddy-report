정적 구현 상태와 독립 인수 판정을 분리한다. C는 해당 구현 경로와 핵심 조건을 소스에서 확인한 충족 추정, P는 부분 구현, M은 필수 경로/보장 누락, D는 구현은 있으나 위반 확인, U는 판단 불가다. C도 실행 인수 PASS를 뜻하지 않는다. 구현 추정율은 (C + 0.5×P + 0.5×D) / 40이며, 요구사항별 비중을 동일하게 둔 A항목 기반 대리지표다. HRMS 전체 문장에 대한 정확한 구현 백분율은 아니다. U가 있으면 단일 구현율 대신 하한~상한을 표시하도록 했고 이번 정적 분류에는 U가 없다.

독립 A판정은 모든 하위 시나리오를 확인했을 때만 PASS, 확인한 일부에서 필수 위반이 있으면 FAIL, 나머지는 NOT_RUN이다. A 검증 커버리지=(PASS+FAIL)/40, A 실행 통과율=PASS/(PASS+FAIL), API 검증 통과율=PASS/실행 수, API 검증 실패율=FAIL/실행 수(미실행은 분모 제외·별도 공개)다. A FAIL은 하위 위반 하나로도 가능하므로 A 커버리지가 모든 하위 시험의 실행 비율을 뜻하지 않는다. 전체 소프트웨어의 실제 버그율·전 코드 정확도는 측정할 수 없다.

같은 문제가 두 영역에 영향을 주면 중복 영향을 공개했다. 예: HY4 직원 화면 중단은 기능에서 “화면으로 완료 불가”, UI에서 “폼 렌더링 실패”를 각각 반영한다. 반면 동일 500의 여러 HTTP 사례는 예외 처리 결함군 하나로 묶고, 결함 건수 자체를 다시 점수에서 차감하지 않았다. 미실행 동시성·복구 시험을 실제 제품 실패로 감점하지 않았고, 제공 시험의 부재/약한 증거는 시험·문서 영역에 반영했다. 코드에서 필수 보장 누락을 확인한 경우에는 미실행과 별개로 구현/정확성/보안에 반영했다.
